# OpenCode ↔ Firestore State Synchronization

## Purpose

OpenCode owns disposable execution/session state. Firestore owns authoritative collaborative product state.

Req Helper must remain correct if OpenCode restarts, loses its local database, compacts history, or continues a session after other users changed the same Delivery Subject.

## State ownership

### Firestore owns

- Delivery Subject lifecycle/scope/revision;
- memberships and perspective assignments;
- source artifacts;
- tasks/messages required for user continuity;
- contributions/evidence/verifications;
- requirements/revisions/provenance;
- gaps/assumptions/conflicts/decisions;
- enterprise references/diffs;
- work packages/acceptance/evals/dependencies;
- readiness;
- DomainEvents;
- AgentThread/AgentRun metadata.

### OpenCode owns only transient execution state

- provider/model conversation state;
- harness-local history;
- temporary tool context;
- internal compaction/cache state.

Never copy `opencode.db` or local files wholesale into Firestore.

## What may be persisted from OpenCode

Persist only product/audit-relevant output:

1. user-visible assistant messages;
2. tool-call metadata needed for audit/debugging;
3. schema-validated structured outputs;
4. proposed commands;
5. applied/rejected command IDs;
6. provider/model/session/run metadata;
7. errors/status/latency.

Never persist hidden chain-of-thought, credentials/tokens, internal caches, or arbitrary local database records.

## Logical AgentThread

Default identity:

```text
subjectId + perspectiveId + participantId
```

The Firestore thread stores:

```ts
{
  id,
  perspectiveId?,
  participantId,
  opencodeSessionId?,
  sessionGeneration,
  status,
  leaseOwner?,
  leaseExpiresAt?,
  contextRevisionPresented?,
  lastMessageAt?,
  lastRunId?,
  createdAt,
  updatedAt
}
```

`sessionGeneration` increments whenever a replacement OpenCode session is created.

### Meaning of contextRevisionPresented

`contextRevisionPresented` is **the highest Delivery Subject revision whose authoritative state was actually presented to the current OpenCode session**.

It is not:

- “the latest Firestore revision that exists”;
- “the domain revision after the run”;
- “the revision generated by this session”.

If a run starts with revision 41, presents revision 41 to OpenCode, and its accepted commands produce revision 44, the thread still has:

```text
contextRevisionPresented = 41
```

until revision 44 (or a later authoritative snapshot) is actually presented in a subsequent prompt/refresh.

This prevents falsely treating a session as aware of normalized downstream effects it has never seen.

## Run lifecycle

```text
1. Receive authenticated user action
2. Authorize subject membership + action capability
3. Persist human message/task answer
4. Load Delivery Subject + AgentThread
5. Acquire AgentThread lease
6. Resolve/recreate OpenCode session
7. Compare current domain revision with contextRevisionPresented
8. Build authoritative bounded ContextEnvelope
9. Persist AgentRun(status=RUNNING)
10. Present context + current message to OpenCode
11. Record the revision actually presented
12. Persist user-visible assistant response/run metadata
13. Validate structured output
14. Re-read affected Firestore objects/revisions
15. Apply allowed idempotent domain commands transactionally
16. Append requirement revisions/verifications/events as applicable
17. Persist domainRevisionAtEnd separately
18. Update task/follow-up state
19. Mark AgentRun succeeded/failed
20. Release lease
```

No domain mutation occurs merely because OpenCode emitted natural-language text.

## Session resolution

If a stored `opencodeSessionId` exists, verify it through OpenCode.

- Valid: reuse.
- Missing/unavailable: create a replacement session, increment `sessionGeneration`, persist mapping and FULL hydrate.

Session loss is normal recovery, not product-data loss.

## Hydration decision

At run start:

```text
currentRevision = deliverySubject.revision
presentedRevision = agentThread.contextRevisionPresented
```

Then:

```text
new/recreated session               -> FULL
presentedRevision missing           -> FULL
currentRevision == presentedRevision -> MINIMAL
currentRevision != presentedRevision -> FULL in P0
```

True DELTA hydration is permitted later, but P0 should prefer correctness and bounded full refresh whenever shared domain state changed.

## Prompt precedence

Every prompt clearly separates:

```text
SYSTEM/SKILL INSTRUCTIONS
AUTHORITATIVE CURRENT STATE (revision N)
BOUNDED CONVERSATION CONTINUITY
CURRENT USER MESSAGE
```

Instruction:

> If conversation/session memory conflicts with AUTHORITATIVE CURRENT STATE, use the authoritative state. Surface the discrepancy when material.

Do not rewrite old transcript entries just because current truth changed.

## Human message durability

When a participant answers:

1. authorize the action;
2. persist the human message and set task `ANSWERED`;
3. begin agent processing and set task `PROCESSING`;
4. invoke OpenCode;
5. persist assistant-visible response;
6. apply valid domain commands;
7. set task `COMPLETED`, `WAITING_ON_OTHER`, or back to `IN_PROGRESS` with follow-up.

If OpenCode fails after step 2, the human's answer remains durable and retriable.

## Structured mutation contract

Typical command:

```ts
{
  commandId,
  idempotencyKey,
  expectedDomainRevision,
  operation,
  targetId,
  expectedTargetRevision?,
  payload,
  provenanceIds
}
```

Before applying:

1. authorize actor/tool;
2. re-read current object/domain revision;
3. verify idempotency key not already applied;
4. reject stale target/domain revision where semantic correctness matters;
5. validate Zod/domain invariants;
6. commit mutation + revisions/provenance/audit atomically where feasible;
7. if stale, recompute rather than last-write-wins.

## Requirement edits

Human and AI edits use the same service path.

A semantic change must:

- append `RequirementRevision`;
- increment requirement revision;
- attach new `RequirementSource` records as appropriate;
- leave old Verification immutable but make it ineligible for the new revision;
- reassess revision-bound acceptance/evals;
- reassess conflicts/gaps that depended on the previous wording.

## Tools

Read-only tools may fetch enterprise/current context.

Mutation tools always call Req Helper application services:

```text
OpenCode
 -> Req Helper tool/API
    -> authz
    -> schema validation
    -> revision/idempotency check
    -> Firestore transaction
    -> audit event
```

OpenCode never receives unrestricted Firestore credentials.

## Concurrency

### Same AgentThread

Serialized by Firestore lease.

### Different AgentThreads

May run concurrently.

### Same domain object

Concurrent proposals are allowed; commits are revision-checked. Semantic collisions create/reopen Conflict or force recomputation.

## Process recovery

### OpenCode unavailable/restarted

- task/human input stays in Firestore;
- AgentRun fails/aborts;
- next attempt recreates session and FULL hydrates.

### Req Helper backend restart

- Firestore remains authoritative;
- expired leases may be reacquired;
- stale RUNNING AgentRuns may be marked ABANDONED/FAILED by recovery logic.

### Duplicate retry

Idempotency key prevents duplicate requirement/source/event application.

## Compaction

Product correctness never depends on OpenCode/provider compaction.

Firestore retains user-visible message history. Req Helper chooses bounded recent messages + authoritative structured context. A fresh OpenCode session may be started at any time.

## Required P0 recovery/concurrency tests

1. deleted OpenCode session does not lose product state;
2. replacement session can continue a task from Firestore;
3. another user's Firestore change is presented before the old session's next meaningful reasoning step;
4. `contextRevisionPresented` is not incorrectly advanced to same-run `domainRevisionAtEnd`;
5. duplicate retry cannot duplicate requirement/revision/event creation;
6. stale mutation is rejected;
7. two independent threads run concurrently;
8. same thread cannot run two prompts concurrently;
9. user-visible history survives OpenCode loss;
10. human answer survives model/provider failure after persistence.
